# 성능 개선 계획 (Lite R-CNN v2/v3)

정확도(COCO AP)와 속도(batch 1 지연 시간)를 올리기 위한 작업 순서, 근거, 기대 효과, 채택 기준을 정리합니다.
실행 방법은 [Colab·4090 실행 안내](COLAB.md), 측정 규칙은 [성능 측정 안내](MEASUREMENT.md)를 보십시오.

## 한눈에 보기

1. **재학습 없는 추론 설정** (지금): Conv+BN 융합, RPN 후보 축소, 고정 캔버스, Soft-NMS, CUDA 그래프.
   CPU 스모크 측정으로 확인했고(2절), T4 효과는 Colab 노트북 단계 B(`scripts/compare_improvements.py`)로 처음 확인합니다.
   CPU에서 `fast`는 AP를 유지하면서 `deploy`보다 v2 25~28%, v3 35~36% 빨랐고, `accurate`는 스모크 AP가 v2 +3.45, v3 +1.75%p 올랐습니다.
2. **v3.1 학습 ablation** (학교 RTX 4090, 12 epoch씩): 앵커 수정 → 증류 순효과 → EMA → RoI 채널 → 증류 손실 수정 → multi-scale.
3. **v3.1 전체 학습** (48 epoch): 2에서 채택한 것만 합쳐 한 번.
4. **하지 않을 것**: 측정상 이득이 없거나 비교를 망치는 것 (아래 4절).

## 1. 근거 수치를 읽는 법

- **CPU 최종 측정**: 4 vCPU Xeon 2.1 GHz 가상 머신(다른 작업과 공유) · PyTorch 2.14.1 · 4스레드에서 `compare_improvements.py`로
  같은 측정을 연달아 두 번 했습니다. 지연 시간은 이미지 16장 × 20라운드(설정마다 320회, 이미지당 20회)를 교차 측정했고, 두 실행 값을 범위로 적습니다 (예: −25~−28%).
- **[95% CI]**: 교차 측정의 라운드를 짝지어 다시 뽑는 bootstrap(2000회)으로 구한 Δp50의 95% 신뢰구간입니다.
  **한 실행 안의 흔들림만** 담습니다. 두 CPU 실행에서 `deploy` 대비 값은 서로 맞았지만(v2 `fast` −25.4 [−31.3, −19.4] / −27.6 [−32.9, −22.0]),
  `baseline` 대비 값은 구간보다 더 움직였고(v2 `deploy` −35.1 [−39.0, −30.8] / −41.5 [−45.8, −36.9]),
  v2 `accurate_fast`의 `deploy` 대비 값은 방향이 뒤집혔습니다(+8.4 [+3.3, +13.1] / −6.7 [−13.2, +0.3]).
- **이전 순차 측정**: 이렇게 표시한 값은 설정마다 따로(다른 시간대에) 잰 예전 값입니다. 같은 측정을 다시 하면 최대 17%p까지 달라졌으므로 참고만 하십시오.
- "스모크 AP"는 COCO **train** 이미지 128장으로 잰 값이라 AP가 부풀려집니다 (v2 42.2% vs 전체 val 28.8%). **방향과 상대 크기만** 참고하십시오.
  128장 기준 AP 차이의 신뢰구간은 ±0.5~1%p입니다. AP는 두 실행에서 똑같았습니다.
- GPU(T4) 숫자는 아직 없습니다. Colab 단계 B에서 나옵니다. 특히 channels_last와 CUDA 그래프는 장치에 따라 결과가 크게 다릅니다.
- 학습 검증 AP(배치 4, 점수 하한 0.05)와 batch 1 평가 AP는 같은 모델도 0.5~1%p 다릅니다. 같은 방식끼리만 비교합니다.

검출 점수 하한 0.05, 지연 시간 16장 × 20라운드 (설정마다 320회). Faster R-CNN은 이 환경에서 가중치를 받을 수 없어 빠졌습니다.

**솔직한 기대치**

- `fast`: 정확도는 그대로(스모크 v2 +0.02, v3 +0.10%p)이고, CPU 지연은 `deploy` 대비 v2 −25~−28%, v3 −35~−36%로 두 실행 모두 구간이 0보다 아래였습니다.
  GPU에서는 RPN 비중이 작아 이득이 더 작을 수 있습니다.
- `accurate`: val에서 **+1~2%p를 기대하지만 검증 전**입니다. 고정 캔버스의 +0.6~0.7%p는 학습 중 검증(배치 4, 패딩 포함)과
  batch 1 평가의 차이에서 추정했고, Soft-NMS는 논문과 스모크 결과입니다. v3는 스모크에서 고정 캔버스 효과가 0에 가까웠습니다.
  고정 캔버스는 RoIAlign 스케일을 캔버스 크기에서 고정해야 맞습니다 (torchvision은 첫 이미지로 스케일을 정해 캐시하므로,
  첫 이미지가 짧으면 이후 모든 이미지의 스케일이 2배로 틀어짐). `apply_inference_options`가 이를 처리합니다.
  CPU 지연 비용은 `deploy` 대비 v3 +2~+3%(두 실행 모두 구간이 0 포함 = 변화 없음), v2 +1~+8%(실행 1만 구간이 0 밖)로 아직 결론이 없습니다.
  `accurate`에서 이미지당 검출이 v2 22→54, v3 23→46개로 늘었고 (대부분 Soft-NMS 몫: 단독 52 / 45개), AR@100도 올랐습니다(v2 48.9→57.5, v3 41.9→49.0).
- `accurate_fast`: **GPU 속도 대안으로만** 둡니다. 스모크 AP가 `accurate`보다 v2 1.3, v3 0.5%p 낮고,
  CPU에서도 `accurate`보다 뚜렷하게 빠르지 않았습니다 (두 설정의 `deploy` 대비 구간이 겹침).
  Matrix NMS는 겹친 상자를 가장 많이 겹친 상자 하나로만 낮추므로 중간 점수 중복이 남아 v2에서 검출 수가 크게 늘었습니다(이미지당 84개).
- `gpu_graph`: GPU에서 한 번도 돌려 보지 않았습니다. 첫 호출에서 캡처한 뒤 eager 결과와 비교해 다르면 eager로 돌아갑니다.
  보고서의 `inference_options.cuda_graph_status.status`가 `captured`인지 확인하십시오. 그래프를 쓰지 못한 측정은 `summary.md`의
  '비교 전에 확인할 점'과 `summary.csv`의 `note`에 남습니다.
- `torch.compile`(옵션 `compile_backbone`, 설정 목록에는 없음): CPU에서 v2 −7%, v3 ≈0(이전 순차 측정)이었고 컴파일 시간이 깁니다. 우선순위 낮음.

**T4 결과로 정하는 규칙** (단계 B, val 5000장, Faster R-CNN 포함)

- 지연 시간 변화는 `summary.md`의 [95% CI]로 판단합니다. **구간이 0을 포함하면 "변화 없음"**입니다.
- 구간은 한 실행 안의 흔들림만 담습니다. 그래서 **10% 안팎보다 작은 차이에 기대는 결정**(채택 기준값 근처인 경우 포함)은
  단계 B를 한 번 더 돌려 같은 결과가 나올 때만 내립니다.
- `deploy`는 항상 채택합니다 (정확도 동일).
- `fast`는 **`baseline`이 아니라 `deploy`와 비교합니다** (`baseline` 대비 값에는 `deploy`의 이득이 섞여 있음).
  v2·v3 모두 ΔAP ≥ −0.1%p이고 `Δp50 vs deploy`의 구간 상한이 0보다 작으면(확실히 빨라지면) 속도 우선 기본값으로 채택합니다.
- `accurate`는 ΔAP ≥ +0.5%p이면 정확도 우선 설정으로 채택하고, p50이 목표(15 ms)를 넘는지 함께 봅니다.
- `accurate_fast`는 `accurate`가 목표 시간을 넘고, `accurate_fast`가 확실히 더 빠를 때(두 설정의 `Δp50 vs deploy` 구간이 겹치지 않음)만
  AP 손실을 감수하고 대신 씁니다.
- `gpu_graph`는 그래프가 캡처되었고 고정 캔버스를 쓰고도 `Δp50 vs deploy`가 −10% 이하이며 구간 상한이 0보다 작으면 GPU 배포 설정으로 채택합니다.
- 보고서에는 세 모델 모두 `baseline`과 채택한 설정을 나란히 적습니다.

## 3. 재학습 ablation (학교 RTX 4090)

### 왜 v3부터 고치나 (128장 진단, 학습 없이 잰 값)

v3는 val AP 26.80%로 v2(28.82%)보다 낮고, 특히 큰 객체(AP_L 38.6 vs 44.5)와 AP75(26.8 vs 29.9)에서 뒤처집니다. 작은 객체는 더 낫습니다(12.2 vs 11.0).

| 지표 | v2 | v3 | v3.1 앵커 |
|---|---:|---:|---:|
| 가장 잘 맞는 앵커의 IoU ≥ 0.7인 정답 비율 | 31% | 8% | 67% |
| 이미지당 RPN positive 앵커 | 41 | 9.5 | 22 |
| 학습 중 이미지당 positive 제안 (IoU ≥ 0.5) | 96 | 26 | – |
| 제안 재현율 R@300, IoU 0.5 / 0.75 (원본 좌표) | 0.91 / 0.74 | 0.92 / 0.46 | – |

- v3는 레벨마다 앵커 크기가 하나(위치당 3개)라 정답과 잘 맞는 앵커가 드물고, RPN과 RoI 헤드의 학습 신호가 약합니다.
  물체는 찾지만(IoU 0.5 재현율은 비슷) 상자가 느슨합니다(IoU 0.75 재현율이 낮음).
- torchvision은 앵커 stride를 `패딩된 크기 // 특징 맵 크기`로 계산해, 정사각형이 아닌 입력에서 P6/P7 앵커가 28~48px 어긋납니다.
  stride를 고정하면 재학습 없이도 큰 객체 R@300(IoU 0.75)이 0.47→0.52로 오릅니다.
- v3.1 앵커(위치당 9개)는 앵커 수가 3배지만 CPU forward 시간 비는 1.00 [0.95, 1.06]이었습니다.
- 현재 feature 증류 손실은 약 (1 − cos)/256이라 v3 학습 기록에서 5e-4 → 4e-4 수준으로 사실상 기울기가 없습니다 (RoI 증류는 0.55 → 0.19).
  teacher의 상자 예측은 증류하지 않았습니다.

### 실험 순서와 채택 기준

공통: `--init-backbone outputs/coco_4090_v2/best.pth`, seed 42, 12 epoch(LR 감소 8/11), 매 epoch val2017 전체 검증(배치 4).
비교 지표는 `history.jsonl`/`RESULTS.md`의 **최고 epoch AP@[.50:.95]**이고, AP75·AP_S·AP_L의 방향도 봅니다.
같은 설정을 다시 돌려도 GPU 비결정성 때문에 ±0.2%p 정도 흔들리므로 **0.2%p 미만 차이는 "같음"**으로 봅니다.

| 순서 | 실험 | config | A1 대비 바뀌는 것 | 질문 | 채택 기준 |
|---|---|---|---|---|---|
| 1 | S0 (12 epoch 기준) | `configs/coco_v3_short.yaml` | v3 그대로, 12 epoch | 12 epoch 기준점 | — |
| 2 | A1 | `configs/coco_v3_1a.yaml` | 위치당 앵커 9개 + 고정 stride | 앵커가 v3의 병목인가 | S0 대비 AP ≥ +0.5%p, AP75·AP_L 상승 |
| 3 | A3 | `configs/coco_v3_1a_nokd.yaml` | 증류 끔 | 지금의 증류가 도움이 되나 | A1이 A3보다 ≥ +0.3%p면 증류 유지, 아니면 끄기 (teacher가 빠져 학습도 빨라짐) |
| 4 | A1+EMA | `configs/coco_v3_1a_ema.yaml` | 가중치 EMA (decay 0.9998, warmup 2000) | 비용 없는 이득이 있나 | ≥ +0.2%p면 채택 |
| 5 | A2 | `configs/coco_v3_1b.yaml` | `roi_channels` 32→64 | RoI 투영이 너무 좁은가 | ≥ +0.3%p이고 p50 증가 ≤ 5% (T4 또는 4090) |
| 6 | KD 수정 | 직접 생성 ([COLAB.md](COLAB.md#3-학교-linux-rtx-4090에서-학습하기)) | `feature_loss: standardized`, `box_weight: 1.0` (값은 검증 전 추정치) | 증류를 제대로 하면 오르나 | ≥ +0.3%p (3에서 증류 효과가 없을 때 특히) |
| 7 | Multi-scale | 직접 생성 (같은 곳) | 짧은 변 384~640 무작위 | 크기 다양성 | ≥ +0.3%p. 12 epoch에서는 불리할 수 있어 낮은 순위 |

- 시간: v3 48 epoch가 4090에서 약 24시간 걸렸으므로(커밋·`RESULTS.md` 시각 기준 추정) 12 epoch 실험 하나는 **약 6~7시간**입니다.
  1~5를 차례로 돌리면 30~35시간이고 1·2가 먼저 끝나므로 그 결과부터 확인합니다. 6·7은 그다음입니다.
- 지연 시간 확인 (새 체크포인트, `baseline`과 `deploy`를 잼):
  `python scripts/compare_improvements.py --models v3 --v3-weights outputs/abl12_v3_1b_anchors_roi64/best.pth --presets deploy --device cuda --limit 500`
  비교할 체크포인트(예: A1 `outputs/abl12_v3_1a_anchors/best.pth`)도 같은 명령으로 잽니다. 체크포인트끼리는 실행이 달라 신뢰구간이
  실행 사이 차이를 담지 못하므로, A1 → A2 → A1 → A2처럼 번갈아 두 번씩 재서 `deploy` 행의 p50을 비교합니다.
- 마지막으로 `configs/coco_v3_1.yaml`(48 epoch, A1과 같은 앵커)에 채택한 옵션만 더해 전체 학습합니다 (A2를 채택하면 `roi_channels: 64`).
  목표는 학습 검증 AP가 v2의 28.82%를 넘는 것이고, 최종 숫자는 Colab 단계 A·B(batch 1, T4)로 다시 잽니다.

## 4. 하지 않을 것

지연 시간 수치는 이전 순차 측정이라 몇 % 차이는 잡음일 수 있습니다 (1절). AP는 스모크 128장 기준입니다.

| 하지 않을 것 | 이유 (측정) |
|---|---|
| RPN 제안 수(NMS 후) 300→100/150 줄이기 | AP v2 −0.81 [−1.34, −0.22], v3 −0.85%p (100개 기준). CPU 이득 −9~10%, GPU에서는 RoI 헤드 비중이 작아 이득이 더 작음 |
| RoI 헤드 NMS 전 후보 상한 (1000개) | AP 변화 0이고 지연 이득도 보이지 않음 (v2 +2.6%, v3 +4.5%) |
| NMS 좌표 오프셋 방식 강제 | torchvision `batched_nms`가 상자 수에 따라 빠른 방식을 이미 고릅니다. 강제해도 이득이 없고 상자가 많으면 느려짐 |
| 재학습 없이 입력을 800으로 키우기 | AP v2 −1.1, v3 −2.0%p (AP_S만 +3%p 안팎), 평가 시간 +40~70% |
| 한 모델에만 점수 하한·NMS·제안 수 바꾸기 | 불공정한 비교. `compare_improvements.py`는 Faster R-CNN에도 같은 설정을 자동 적용 |
| 학습 검증 AP와 batch 1 평가 AP, 단계 A(하한 0.001)와 단계 B(하한 0.05) AP를 섞기 | 같은 모델도 0.5~1%p 차이. 하한이 낮을수록 AP가 유리 |
| 128장 스모크 AP로 결론 내기 | 학습 이미지라 부풀려지고 신뢰구간이 ±0.5~1%p |
| CPU의 channels_last 이득을 GPU에 그대로 기대하기 | 장치마다 다름. GPU는 자동 규칙상 꺼져 있고 아직 재지 않음 |

## 5. 결과 읽는 법

- `outputs/improvements/<실행>/summary.md`: 모델 × 설정 표. **ΔAP**는 같은 모델 `baseline` 대비 %p입니다.
  **Δp50 (%) [95% CI]**는 `baseline` 대비, **Δp50 vs deploy (%) [95% CI]**는 `deploy` 대비 p50 변화율입니다 (음수 = 빨라짐).
  `summary.csv`에는 같은 값과 구간 끝(`delta_p50_ci_low`, `delta_p50_ci_high`, `delta_p50_vs_deploy_ci_low`, `delta_p50_vs_deploy_ci_high`)이 열로 있습니다.
- [95% CI] 읽기: `−25.4 [−31.3, −19.4]`는 "이번 실행에서 p50이 25.4% 줄었고, 실행 안의 흔들림을 감안해도 19.4~31.3% 줄었다"는 뜻입니다.
  **구간이 0을 포함하면 변화 없음**입니다. 다른 실행과의 차이는 담지 않으므로, 10% 안팎의 차이는 한 번 더 재서 확인합니다 (2절 규칙).
  `--sequential-latency`로 잰 결과에는 구간이 없습니다.
- 정확도: 같은 5000장을 짝지어 비교하므로 **|ΔAP| < 0.1%p**는 같은 것으로 봅니다.
  구간이 없는 값(p95, FPS, 순차 측정의 p50)은 **3% 미만** 변화를 같은 것으로 봅니다 (대시보드 판정도 같은 기준). p95는 p50보다 더 흔들립니다.
- "비교 전에 확인할 점"에 `[비교 불가]`가 있으면 그 행은 쓰지 않습니다.
- Lite R-CNN의 GPU 지연은 파이썬·커널 실행 오버헤드(CPU) 비중이 커서 Colab의 느린 CPU에서 불리하게 나옵니다. 같은 실행 안에서만 비교합니다.
- 대시보드: 저장소 폴더에서 `streamlit run dashboard/app.py`를 실행하고, 사이드바 **결과 폴더**에 `outputs/improvements/<실행>/reports`를
  넣습니다 (어느 셸에서나 됨). 이 폴더에는 v2와 v3가 함께 있으므로 사이드바 **Light R-CNN 체크포인트**에서 버전을 고르고
  (버전별 폴더 `reports/v2`·`reports/v3`를 넣어도 됨), **추론 설정**을 바꿔 가며 **개선 전/후** 탭을 봅니다.
  그 탭의 p50 변화에는 `baseline` 대비 95% CI와 판정('좋아짐', '나빠짐', '변화 없음 (오차 범위)')이 붙습니다.
  `fast`를 판단할 `deploy` 대비 값은 `summary.md`의 `Δp50 vs deploy` 열에서 봅니다.
